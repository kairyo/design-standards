# 排版、层级与局部润色

分类：`TEAM_RECOMMENDATION`。仅补充与当前问题相关的判断，不是固定风格、数值、技术栈或完整无障碍清单。

## 从任务确定文字角色与密度

先辨认用户在操作、检索、持续阅读还是被介绍一个产品。同一页面可以包含不同区域，不要求整页套一种密度。依据当前任务判断哪些信息先被看见、哪些需要一起比较；不要为了制造焦点而隐藏必要数据或把所有按钮都弱化。

检查标题、正文、标签、辅助信息和数值在实际画面中的分工。相邻角色可以通过字重、空间、颜色或位置区分，不只靠增大字号；相同角色跨组件和状态保持一致。沿用批准的字体与 token；系统字体也可以是明确的项目选择，不因“常见”就换掉。只有确实需要表达不同角色时才建议增加字体。

在真实语言与容器中检查换行、行高和行长；中文、混合文字与拉丁段落不共用固定字符数标准。选择会改变结论的长标题、数字、窄窗口和文字放大样本。若有自定义字体，另查回退与加载；没有加载证据就不声称字体交付通过。字号比例、间距基数、圆角公式和动效时长由项目决定。

检查组内关系是否紧密、组间边界是否清楚，必要操作是否容易发现。更疏不必然更高级，更密不必然更高效；记录一屏信息量、滚动与比较成本的取舍。大标题、卡片、色块或动效是否值得加入，要能说明它服务哪项任务或识别特征。

## 在已有方向内润色

定位问题属于组件使用偏差、共享样式偏差还是局部例外，建议改动最小的正确归属；不要为一个例外另造全局 token 系统。比对相邻内容的基线、视觉重心、间距和状态；光学调整需要实际画面，不机械加减固定像素。

颜色继续承担原有的操作、状态、内容和品牌含义。不要为了让页面显得安静而削弱焦点、错误或必要边界，也不要在润色中偷偷换主题、重排流程、删文案或增加动效。确需改变这些决定时，说明原因与授权范围。

实施获准后，用对应画面检查改动，并走受影响的路径：如“打开条目—返回原列表”，或“纠错—首次提交—确认结果”。只测发生关系的状态与输入方式；读屏、真实设备或字体加载等缺证项单独记录，不能由截图或静态规则替代。
