# 表单提交与纠错：完整合成示例

这是原创、未执行的设计示例，不对应真实产品或用户数据。方法属于 `TEAM_RECOMMENDATION`；下列字段、状态、文案和服务前提属于合成项目的 `PROJECT_CHOICE`。所有产品运行检查均为 `NOT_RUN`，没有实现、截图、读屏或服务写入证据。

## 1. Brief 与明确的前提

按 [设计 brief 模板](../templates/design-brief.md)填写：

| 字段 | 本例的合成选择与待确认项 |
| --- | --- |
| 任务 | 用户在阅读工具中创建一份清单；成功是服务确认创建且用户可查看该清单，不是按钮播放成功动画 |
| 平台与环境 | 用 Web 场景说明键盘、指针和读屏操作；具体浏览器/辅助技术版本、窗口及支持语言由采用项目补齐。原生项目另做平台映射 |
| 内容与语义 | 名称必填，去掉首尾空白后不能为空，当前空间内不重名；说明选填；排序预选“最近添加”，可改为“标题”。其他限制不得从示例猜测 |
| 已有决定 | 复用项目批准的字段、选择器、按钮和状态反馈组件。具体设计版本、品牌数值和组件标识尚未绑定；这些未补齐前不能进入项目实现验收 |
| 探索问题 | 如何一起核对信息、找到错误并保留输入；是否确有分组或分步的必要 |
| 候选差异 / 模式选择与代价 | 见第 2 节；本合成例暂选单页，须验证长错误文案和大字下的定位成本 |
| 行为与恢复 | 提交时统一校验；区分字段拒绝、可重试失败、不可重试整单拒绝和结果未知，失败不清空其他输入；具体转换见第 3 节 |
| 验证重点 | 填写—提交—纠错—重试—成功；同时检查重复操作、晚到响应和辅助输入，第 6 节只列待执行项 |
| 决策 | 本例的选择用于讨论。实际采用由项目指定负责人决定；支持矩阵、服务前提或设计版本未确认时记录缺口；完成约定范围后停止，不扩展到账号、支付或真实数据 |

本例假定服务能区分“字段拒绝且未创建”“当前条件下不可重试的整单拒绝且未创建”“明确未创建的临时失败”“确认创建”，并能按一次提交标识查询结果、防止同一提交重复创建。明确拒绝或可重试失败还须确认原请求已终止、不会继续写入。具体协议与实现不在本例规定。实际项目若没有这些能力，不得把未知结果直接标为可安全重试；相关恢复验收记 `BLOCKED`，先解决能力或产品流程缺口。不能仅凭 HTTP 错误码、超时或客户端取消，断言服务没有写入。

合成输入组 A：既有清单名“周末阅读”；新清单先输入同名，后改为“旅行阅读”；说明为“收集途中想读的文章。”；排序主动改为非默认的“标题”，以便发现纠错时意外重置。正常初始预选仍为“最近添加”。这些是假定测试数据，不连接真实账号，也不实际发出请求。

整单拒绝情境：所有字段合法，但提交时目标空间已转为只读；服务确认未创建、原请求已终止，改名无效，当前用户无权解除只读。直接响应或后续查询都可能确认这一结果。此情境只用于讨论，不改变真实空间权限。

## 2. 模式比较与选择

| 候选 | 本例的判断 | 改变判断的条件 |
| --- | --- | --- |
| 单页 | 暂选。三项信息共同决定一份清单，没有前后依赖，可在提交前一起核对 | 长内容或真实任务使页面难以理解时重新评估，不能只凭字段数作决定 |
| 单页分组 | 暂不选。当前没有值得单独命名的主题组；分组会增加层级 | 后续出现意义清楚、需要跨组核对的信息时比较 |
| 分步 | 暂不选。当前拆步会增加返回纠错的成本，没有对应的依赖收益 | 出现真实分支或后一步依赖前一步时，再定义返回、草稿保留与后续内容失效规则 |

这是一项待验证的设计选择，不声称单页更高效或已获得用户研究支持。模式比较方法的外部参考为 [S18](../references/sources.md#s18)；本例的清单任务及具体行为均为原创假设。

## 3. 状态、触发与恢复

表单状态与每个字段的错误记录分开。初次打开为 `editing`，不立即给未填写的名称报错；点击“创建清单”或等价键盘提交时统一校验。名称为空则进入 `invalid`，焦点到名称字段，显示“填写清单名称”。已报错字段再次编辑后标为待重验，在失焦或下次提交时更新错误；不逐字播报、不清空其他字段。修改名称使旧的同名拒绝失效，但不表示新名称已经获服务接受。

| 状态 | 进入条件与可见结果 | 可操作性、焦点与下一步 |
| --- | --- | --- |
| `editing` 编辑中 | 正在填写，尚未取得提交结果；标签、必填说明与当前值可见 | 可编辑与提交；本地不合法 → `invalid`，本地通过 → `submitting` |
| `invalid` 字段需修正 | 本地校验失败，或服务明确拒绝名称且未创建；字段旁显示原因 | 保留全部输入，提供“修改名称”定位入口；本地同步报错可聚焦名称，异步拒绝不抢走用户已转移的焦点。编辑并重验后无已知错误 → `editing`；再次提交本地通过 → `submitting`，唯一性仍由服务判断 |
| `submitting` 提交中 | 已捕获本次输入与提交标识；显示“正在创建清单…” | 字段暂不可编辑但仍可阅读，所有提交入口共用防重复状态；保持焦点可追踪。响应匹配本次提交后，分别进入 `invalid`、`failed_retryable`、`rejected` 或 `succeeded`；失去确定结果 → `outcome_unknown` |
| `failed_retryable` 确认未保存 | 服务明确确认未创建且失败可重试；显示“这次没有保存，内容已保留，可以重试” | 修改 → `editing`；重试前重新校验，不合法 → `invalid`，通过 → `submitting`；服务侧防重复与提交标识的使用按实际契约验证，不能靠按钮外观推断 |
| `rejected` 不可重试的整单拒绝 | 服务确认目标空间只读、未创建且原请求不会继续生效；显示“此空间已设为只读，这次未创建清单。可复制填写内容后返回” | 保留可选择复制的输入摘要和“返回清单”入口；不提供无效的改名纠错、重试或继续查询。不抢走仍适用的焦点；若原焦点控件被移除，接续到拒绝说明，再可顺序到达保留内容与返回入口。当前只读条件下不再进入提交 |
| `outcome_unknown` 结果未确认 | 超时、断连或无法解释的响应；显示“还不能确认是否已创建，填写内容已保留” | 保留输入为只读和本次标识，暂不新建另一份提交；提供“查询结果” → `checking_outcome`，没有查询能力则记录阻塞，不伪装成失败或成功 |
| `checking_outcome` 查询中 | 用户主动查询同一提交的结果；显示“正在确认结果…” | 输入仍为只读，不并发查询或再次提交；确认已创建 → `succeeded`；确认字段拒绝且未创建 → `invalid`，恢复编辑并展示字段原因；确认未创建、失败可重试且原请求不会继续生效 → `failed_retryable`；确认只读整单拒绝、未创建且原请求已终止 → `rejected`；仍不确定 → `outcome_unknown`。不无界轮询 |
| `succeeded` 已确认创建 | 服务返回本次创建结果；同页显示“清单已创建”和“查看清单” | 保留可理解的结果及输入摘要，不再发出创建请求；通过状态消息告知结果，焦点所在元素保持可用且可追踪，用户主动查看后再导航 |

补充约束：

- 所有失败状态保留名称、说明与排序；本例只保证当前页面会话内保留，刷新、关闭或跨设备草稿不在承诺内。编辑中离开且有未保存内容时说明后果；提交中或结果未知时离开也不能声称“已取消服务操作”。具体退出处理需项目确认。
- 提交中按本次输入快照解释响应；晚到响应只能影响对应提交，不能覆盖新的输入或已经确认的结果。输入改变后不得把旧的查询/提交标识当作新内容的证明。
- 本例将明确拒绝名称的提示写为“这个名称已在使用，请换一个名称”，保留原值；未知原因不能伪装成用户填错，也不展示原始服务堆栈。
- 进入提交中时即拦截按钮、键盘等重复入口；实际是否只产生一份清单仍需服务结果证据。客户端防重复与服务端防重复分别验证。
- `rejected` 表示当前条件下的拒绝，不等于永远无法创建；后续条件变化后的重新发起流程需项目另行定义。状态表也不穷尽所有服务结果：例如已知未创建但重试条件未确认时，应保留“未创建”的事实并说明恢复条件待确认，不直接提供重试，也不改写成“是否创建未知”。

## 4. 组件、语义变量与交接

以下名称仅示意角色，不代表已有 Figma 节点、代码接口或导出文件：

| 角色 | 输入与行为 | 语义映射及待核验项 |
| --- | --- | --- |
| 名称字段 | 值、标签、必填、说明、对应当前值的错误；保持标签与错误的可访问关联 | `field.error.text` → `text.feedback.error` → 当前主题基础颜色；核对引用链、模式及覆盖，错误还需文字与语义 |
| 提交控件 | 当前表单状态、操作名称、是否允许执行；各种触发共用提交判断 | `action.primary` 与 `focus.indicator` 对应实际组件样式；核对提交中及返回可操作时的焦点表现 |
| 状态反馈 | 正在处理、明确失败、未知、成功及下一步操作；同一结果避免重复通知 | `text.feedback.error` / `text.feedback.success` 只决定视觉角色，不替代消息内容、辅助语义或结果判断 |

采用项目需补齐来源设计/组件版本、属性绑定、token 类型和模式、别名解析、覆盖顺序、平台输出位置及实际消费者，再对照第 6 节检查。此处没有填写品牌数值、真实节点或虚构的导出成功记录；追踪方法见 [04 章](../docs/04-design-systems.md)及 [S19](../references/sources.md#s19)。

## 5. 预期操作路径与无障碍反馈

1. 进入表单，按标签理解名称、说明和排序；用键盘或辅助技术到达每项与提交操作。空白提交应定位名称并解释必填，不能只让边框变红。
2. 按输入组 A 填写同名及其他内容后提交；等待期间能知道正在处理。服务拒绝时显示字段原因与“修改名称”，其他输入保持；异步结果不强行打断已经转移的焦点。
3. 激活“修改名称”到达字段，读到名称、当前值及错误；改为“旅行阅读”，在约定时机更新错误，保留说明和排序，再次提交。核对新提交标识、返回记录与实际内容，确认创建的是本次“旅行阅读”及对应说明、排序，不能只观察按钮恢复或出现成功文字。
4. 若已确认未保存且可重试，可按说明重试；若结果未知，先确认同一提交的结果。两者的文案、动作和辅助语义必须可区分。
5. 若确认只读整单拒绝，说明原因与未创建结果，保留内容供复制并允许返回；不再要求改名、重试或反复查询，也不执行权限修改。
6. 确认成功后获知结果并能主动查看清单；同页状态消息无需为了被读到而反复抢焦点。不能只靠短暂 toast、颜色或动画说明完成。

每条路径在项目支持的输入方式与辅助技术中实际执行；主题、大字、长错误文案和适用的 RTL 内容分别检查。Web 条款与平台边界见 [07 章](../docs/07-inclusive-design.md)及 [S12](../references/sources.md#s12)。上述焦点与文案是本例方案，不是 WCAG 规定的唯一实现。

这里的 F01–F12 是本示例内的检查编号，不是全仓库强制编号方案。模拟服务仅能验证受控情境；真实服务、设备和辅助技术证据仍须分别记录。当前没有执行自动扫描；若后续工具输出 `incomplete`，保留原结果并另记尚未执行的人工检查，不能填 `PASS`。[S21](../references/sources.md#s21)

若实际发现失败，按模板补充用户影响、严重程度、处理优先级、修复与复验。例如“确认后出现两份清单”应检查真实结果及对应提交，不能只改按钮动画就结案。没有观察到这个现象前，不建立虚假的缺陷或修复记录。任何例外都保留原结论、范围和批准状态；作者推演、独立文档复核与产品最终签收分别记录。
