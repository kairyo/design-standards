# 07 本地化、主题与无障碍

默认分类：`TEAM_RECOMMENDATION`。语言数量、发布市场和支持矩阵属于 `PROJECT_CHOICE`；不预设固定六语或其他固定数量。

## 内容在变化时仍能用

采用项目实际语言和内容源。检查长标题、复合词、换行、标点、双向文本、日期数字格式及字体 fallback。伪本地化可暴露空间风险，但不代替真实语言审阅；不得为了截图整齐而擅自改产品语义。

大字时允许布局重排和容器增高，关键内容不因固定高度被裁掉。深浅主题分别检查正文、图标、边界、图片、禁用态与反馈；不能把简单反色当成主题设计。

Apple 的无障碍指导涵盖文字放大、颜色以外的提示、VoiceOver、控制尺寸与替代输入；这些是平台设计依据，不是一次自动扫描即可完成的证明。[S03](../references/sources.md#s03)

Android 的指导强调可理解的标签、辅助操作、标准控件能力与非颜色提示。自定义控件应暴露作用、状态和可执行动作。[S11](../references/sources.md#s11)

## 用真实任务检查可访问性

检查阅读/焦点顺序是否符合任务，装饰是否造成噪声，控件名称是否明确，状态变化是否被传达。仅有手势的核心操作应有可用替代路径。实际命中区域、相邻目标间距与视觉尺寸分别核对，不把图标尺寸当作点击面积。

针对目标平台核对触达建议和单位，不设跨平台单一数值。开启项目支持的大字、读屏、键盘和减少动态效果等设置完成关键流程；减少动效时仍传达状态变化，不把信息随动画一起删除。

## 沿表单提交与纠错路径检查

下列是 `TEAM_RECOMMENDATION` 的操作检查方法；具体焦点落点和反馈形式需按表单结构、平台与任务验证。React Aria 将语义、输入交互、焦点和状态通知列为组件能力，同时要求产品提供可理解的标签和可访问的视觉设计；采用组件库不能代替这些检查。[S20](../references/sources.md#s20)

| 操作 | 观察与验证 |
| --- | --- |
| 开始填写 | 持续可见的标签、必填/选填和格式说明能被理解；辅助技术能识别名称、作用与值，不依赖占位文字代替标签 |
| 提交后出现错误 | 指明哪个字段、出了什么问题和可行的修正办法；通过文字及关联语义传达，不只变红。已填的其他内容仍在 |
| 定位并修正 | 单处错误可引导到字段；多处或跨步骤错误可提供摘要及定位入口。具体焦点策略须记录；异步响应不随意打断用户已转移到别处的操作 |
| 返回修改前序选择 | 检查保留草稿、有效字段和失效步骤的说明；分别观察切换时、主动进入下一步及返回补填后的焦点位置与状态通知 |
| 再次提交 | 编辑时更新相关字段错误，提交时仍检查完整提交条件；键盘与辅助技术可以触发恢复操作，不会被禁用控件困住 |
| 等待与获得结果 | 加载、可重试失败、不可重试的整单拒绝、结果未知和成功有可感知的状态说明；恢复操作符合实际条件，避免重复播报和非必要的焦点跳转；成功有明确的后续操作 |

已确认的字段错误，不得仅因字段获得或失去焦点而消失。记录错误清除或转为待重验的触发条件，分别核对用户只是回看、确实编辑和重新提交三种情况；不能把一次焦点切换当作内容已纠正。

焦点验收记录动作前的位置、动作后应保持或转移的条件、可核对的目标，以及继续顺序导航时到达的控件。“焦点合理”或“入口可达”不够具体：现有焦点仍适用时可保持；焦点所在控件被移除或隐藏时需有明确接续目标，不能落到不可操作的位置；用户主动进入另一步或激活错误定位时，按方案到达相应标题或字段。状态更新本身不统一触发跳转，也不覆盖用户在异步等待期间的新焦点。具体选择与读屏反馈见 [分步往返示例](../examples/stepped-form-branch-return.md)，不作为所有平台的固定落点。

`OFFICIAL_REQUIREMENT`（条件性条款定位）：Web 若声明 WCAG 2.2 AA 符合性，应同时核对 2.4.3 焦点顺序、3.3.1 错误识别、3.3.2 标签或说明、3.3.3 错误建议、4.1.2 名称/角色/值和 4.1.3 状态消息等适用条款；3.3.3 包含安全或内容目的相关例外。此处列举不是完整符合性检查，也不表示 WCAG 强制采用某一种错误摘要或焦点跳转方案。[S12](../references/sources.md#s12)

在支持范围内，用键盘和实际辅助技术分别走完失败、纠正、重试与成功。再检查长错误文案、大字、主题和适用的 RTL 内容；记录执行过的环境，不把一次视觉检查扩展成所有输入方式通过。原生平台通过相应语义与焦点机制验证，不照搬网页属性名。

[完整表单示例](../examples/form-submit-recovery.md)列出具体动作与待执行检查；未取得运行证据前，例子的存在不能证明流程可访问。

## WCAG 的适用边界

`OFFICIAL_REQUIREMENT`（条件性）：若对 Web 内容声明 WCAG 2.2 AA 符合性，应满足其 A/AA 成功准则与全部符合性要求，包括完整页面、完整流程及相应技术支持条件；局部截图、单个组件或自动扫描结果不足以支撑整站声明。精确要求以固定版本原文为准。[S12](../references/sources.md#s12)

`TEAM_RECOMMENDATION`：Web 项目可选择 WCAG 2.2 AA 作为设计与验收目标，但目标不等于已达标。此处不提供完整符合性清单或法律判断。

原生客户端可借鉴 WCAG 的原则与适用技术指标，但不能直接照搬网页符合性声明。WCAG2ICT 是非规范性的非 Web 应用指导，不自行设置认证要求；原生还需核对平台及项目实际适用的要求。[S15](../references/sources.md#s15)

## 记录未覆盖项

结果应写明平台、版本、范围、输入方式、所用辅助技术和实际动作。主题通过不代表读屏通过，视觉对比通过不代表键盘通过；不可访问的关键流程应作为真实缺陷处理，而不只列为美化建议。
