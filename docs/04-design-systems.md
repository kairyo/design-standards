# 04 设计系统与素材

分类：`TEAM_RECOMMENDATION`；品牌数值与实现映射属于 `PROJECT_CHOICE`。

## 用语义而不是位置命名

从实际复用需求建立 token。可区分基础值、语义角色和必要的组件级覆盖，例如 `text.primary`、`surface.raised`、`action.destructive`。名称只是原创示例，不是必须照抄的 schema。每个角色应说明用途、主题、状态、平台映射和废弃替代项，避免出现大量同义 token。

跨工具交换可评估 DTCG Format 2025.10；它定义交换格式，不替团队决定品牌、命名体系或技术栈，也不是 W3C Recommendation。声称兼容时应对照实际规范和工具支持验证，不能仅因 JSON 中出现 `$value` 就声称符合。[S13](../references/sources.md#s13)

## 从来源追到实际使用

对本次改动涉及的 token，记录来源及版本、语义用途、类型与单位、别名引用链、主题/模式、覆盖顺序、导出位置和实际消费者。Style Dictionary 文档中的来源元数据、引用及冲突说明提供了一种追踪思路；这里采用记录方法，不规定项目必须使用该工具或沿用它的合并行为。[S19](../references/sources.md#s19)

例如，合成表单的 `field.error.text` 引用 `text.feedback.error`，再解析到项目当前主题的基础颜色。交接时应能说明选择了哪个模式、是否有组件覆盖、输出到了哪里、哪个字段错误组件实际使用。名字相同不证明解析值相同，导出成功也不证明运行时已加载。

在获准的隔离范围，可用 [Figma 变量示例](../examples/figma-variable-theme.md)检查单个值变化如何传到样本与消费者，再恢复原值、绑定和模式。核对结构读回、说明标签与实际画面；设计工具内的传播结果不能代替导出器和运行消费者的验证。

发现缺失引用、循环、同名冲突或类型/单位不匹配时，记录受影响角色和消费者，先查清来源再采用；不要静默补值或以工具默认覆盖顺序冒充批准决定。颜色、尺寸和字体分别核对平台映射及实际渲染；示例不提供全局色值或 pt/dp/px 换算表。

共享角色改名、改变含义或废弃时，注明替代项、受影响消费者与迁移条件；具体兼容期限由项目决定。无需为没有复用需求的一次性值制造整套 token 层级。

## 字体与节奏

为标题、正文、标签、数据等角色说明家族、字重、行高、缩放行为、语言覆盖与 fallback。不要让 fallback 悄悄改变布局或把文本转成图片来逃避字体问题。间距、圆角、描边与阴影需要可解释的层级，不要求所有产品采用同一套数值。

## 单位、精度和几何

设计值、布局值、栅格像素、截图缩放和矢量坐标是不同层次。Apple 的 pt、Android 的 dp/sp、Web 的 CSS px/rem 不能按显示数字直接互换；具体映射由平台实现和缩放环境确认。

不强制所有 UI 尺寸或矢量坐标为整数。弹性布局、文字度量、比例分配和路径控制点都可能合理地产生小数；需要锐利栅格边缘时才在实际渲染比例下评估像素对齐。不得通过全局取整破坏间距累计、比例、缩放或命中区域。DTCG 的 dimension 格式也允许数值含小数，但格式可表达不等于每个平台映射天然正确。[S13](../references/sources.md#s13)

## 图标、字体和图片

先确认来源、版本、许可、可修改与分发范围，再确认风格一致性。记录图标语义、视觉尺寸与实际命中区域；装饰图标与操作图标的无障碍策略不同。不要把“系统里有”“购买过”或“网上能下载”当成跨平台分发依据。

图像区分等比例适配与明确裁剪，说明焦点和不可裁内容；不拉伸图片填满容器。图标基线、描边重量和光学居中需实际查看，不能靠统一 bounding box 宣称一致。无需把文字、控件和动态数据烘焙进位图。

公开系统文档只记录方法与权利来源，不携带项目资产。一个平台的符号、字体或 UI 套件也不能默认移植到另一平台。

## 小而可靠的组件契约

记录职责、输入、状态、布局行为、辅助语义及适用平台。组件通过不代表所有页面通过；改共享 token 或组件时扩展到实际受影响消费者，不为“统一”重建已有稳定控件。

## 把状态写成可执行的行为

组件状态说明需要同时覆盖视觉、交互和数据，而不只是列出 default、error、loading 的图片。可按下表补充受影响部分；属性名称和实现方式属于 `PROJECT_CHOICE`。

| 说明项 | 表单中需要回答的问题 |
| --- | --- |
| 输入与职责 | 字段接收哪些值、规则及错误信息；表单与服务分别决定哪些校验结果 |
| 触发与转换 | 在输入、失焦还是提交时校验；什么响应才能进入成功、字段拒绝、可重试失败、不可重试的整单拒绝或结果未知 |
| 保留与失效 | 失败后哪些输入保留；修改前序选择时哪些草稿不再参与当前校验与提交、哪些步骤和确认失效；旧响应是否仍对应当前提交 |
| 可操作性 | 提交中哪些操作可用；按钮、键盘等入口如何避免重复提交；恢复操作是否确有前提 |
| 焦点与反馈 | 变化后焦点在哪里、如何找到错误、辅助技术如何获知状态；不能只靠颜色或旋转图标 |
| 映射与验证 | 组件属性、语义 token、平台实现及对应验收项分别是什么；哪些尚未绑定或实测 |

字段错误与整单提交状态分开：某字段改成合法格式，不表示服务已接受；请求结束也不表示业务成功。无法确认是否保存时，先呈现不确定结果和获准的确认路径，不直接重复创建。防重复与结果查询依赖实际实现能力，不能仅靠按钮变灰宣称成立。

失败结果分别说明影响字段还是整单、业务结果是否确定，以及当前条件下是否可重试。已确认未保存且不可重试的整单拒绝，应说明原因和真实可用的后续操作，不归为字段错误、结果未知或可重试失败。结果已确定但重试条件不明时，保留已知结果并记录恢复条件缺口，不能反过来声称是否保存也未知；仅凭错误码不能推定这些条件。

分支草稿、当前有效输入、步骤完成状态和确认内容分别管理。前序变更只使依赖它的部分失效；非活动分支草稿不进入当前校验、确认摘要或提交数据。切回时恢复内容并按当前条件重验，再生成对应确认，不能沿用旧的完成标记。[分步往返示例](../examples/stepped-form-branch-return.md)说明这四者如何对应；名称和存储方式仍由项目决定。

[完整表单示例](../examples/form-submit-recovery.md)提供状态转换、组件职责和 token 映射。其状态名、重试前提与文案是合成项目选择，不能自动成为所有组件的统一接口。
