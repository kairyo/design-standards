# 08 实现与验收

分类：`TEAM_RECOMMENDATION`。本章规定如何描述证据，不替代具体项目的权限、发布流程或最终放行者。

## 输入与映射

实现前确认批准设计、产品行为、内容来源、组件/样式/变量映射、可写范围和保护区域。无法定位版本或存在冲突时，先报告该缺口，不从旧截图猜测目标。

对应设计能力与代码能力：组件存在不表示状态齐全，设计变量绑定不表示运行主题正确，设计稿批准不表示实现完成。优先复用已有实现，必要的新增接口说明职责与平台差异。

## 先证明看到的是哪个版本

原生运行验收应建立可追溯链：源版本 → 构建记录 → 产物 → 已安装版本 → 当前运行实例。Web 对应源版本 → 构建/部署产物 → 实际加载页面与资源版本。必要时校验关键文件哈希，避免只看标题、设备名或版本字符串。

这不要求所有项目使用云构建；本地、CI 或云端路径由项目选择。构建成功不等于安装成功，更不等于运行中的就是新版本。无法确认时缩小结论范围。

## 分开六种结论

| 层次 | 能说明什么 | 不能单独说明什么 |
| --- | --- | --- |
| 静态/结构检查 | 规则、引用、类型或数据契约符合所检条件 | 实际视觉与交互正确 |
| 视觉检查 | 指定环境和状态下的层级、字体、几何与素材表现 | 点击、焦点、返回或状态恢复 |
| 功能检查 | 执行的动作与业务结果符合预期 | 未覆盖平台的外观和系统行为 |
| 运行环境检查 | 指定系统/窗口/输入中的真实行为 | 所有设备长期稳定 |
| 独立审阅 | 另一位审阅者已复核指定证据与结论 | 用户审美偏好和最终放行 |
| 用户确认 | 用户确认了说明过的目标与范围 | 自动扩大到其他状态或版本 |

工具退出成功、截图生成、测试跳过均不是产品通过的同义词。

[Figma 变量与主题示例](../examples/figma-variable-theme.md)把绑定读回、实际画面、模式往返与恢复拆成七项待执行检查。即使这些检查通过，结论也只覆盖所测设计文件与范围；代码主题加载、辅助技术和业务路径继续另验。

## 测试矩阵按风险建立

覆盖本次目标和受影响状态：窗口阈值两侧、横纵方向、支持语言、主题、大字、空白/加载/失败、长内容、滚动/展开/返回。共享组件、字体或导航改动扩大到受影响消费者；小文案改动无需机械运行无关设备全矩阵，但不能删去既有交付义务。

输入使用合成且归属明确的 fixture，记录选中项、内容版本和环境条件。不要覆盖真实用户资料、修改系统日期或伪造业务结果来匹配设计。fixture、身份链和原始证据存于各项目获准位置，不提交到本公共仓库。

### 自适应改版的覆盖与联合复验

对本次受影响范围建立“页面/流程 × 支持形态 × 相关状态”矩阵，注明原稿依据、功能入口和到达路径、素材用途、应保留的状态及证据层次。支持形态来自项目范围，不由本仓库固定设备数量或尺寸。默认页面通过不能替代其加载、失败、权限、键盘或菜单状态；按风险选择代表性组合时，列出未覆盖项、选择理由和补验条件。

把以下检查拆成可独立判定的结果，再确认它们组合后仍成立：

- 功能入口、目的地与适用条件相符，布局变化不丢失约定保留的任务状态。
- 图片用途、素材/容器/显示比例与焦点符合 [04 章](04-design-systems.md)，当前显示范围及未核验部分明确。
- 视口外内容有可发现的提示和可用的到达路径；静态提示与实际操作分别记录。
- 尺寸变化后的文字、相邻分类/列表、浮层锚点和操作安全区域仍正确，避免修复一项后引入另一项退化。

原稿遗留、适配新增、后续修复引入及来源未明的问题分别记录。归因需要同条件的原稿与目标证据；证据不足时保留“来源未明”，不能依据猜测归责。原稿遗留也可能影响验收，需列影响与处理决定；本次范围外问题继续保留，不随局部修复标为通过。

[验收模板](../templates/verification-record.md)提供矩阵字段，[合成案例](../examples/adaptive-fidelity-regression.md)展示图片比例修正后丢失滚动提示的联合复验。它们是方法示例，未执行的产品检查保持 `NOT_RUN`。

## 观察、操作、比较

先确认输入与截图通道指向同一目标；同一设备/窗口串行操作。保留原始截图，再做必要的标注副本。截图黑屏、缺屏、预览旋转或工具超时可能是观察通道问题，也可能与应用问题并存，不能不经核对就判根因。

交互必须执行真实动作，并检查业务状态及可见结果；不要用重启、换页或重置数据代替需要验证的返回、恢复和滚动行为。读取尺寸时注明坐标空间、逻辑单位、缩放和测量时点。

已确认 bug 使用同目标、可比较条件的 before/after；保留首次失败和中间状态。纯设计探索不制造失败基线。保护区域应采用与风险相称的差异/回归检查，不重新签署历史哈希来掩盖范围外变更。

## 问题影响、处理优先级与复验

沿用 [验收记录模板](../templates/verification-record.md)中的前置、动作、预期、实际及证据，再对发现的问题补充用户影响、受影响状态/人群、是否有替代路径、处理优先级与理由、修复负责人和复验入口。结果状态与处理顺序分开：一个 `FAIL` 不会因暂缓处理变成 `PASS`，截图差异大小也不代表问题影响大小。

可优先讨论阻断核心任务、丢失输入、重复产生业务结果或使某类用户无法完成操作的问题，再判断其他不一致；具体严重程度和处理时限服从项目约定，不新增统一评分、截止时间或发布权限。若申请例外，保留原问题及未覆盖项，注明范围、批准角色、补偿措施和复验触发条件；没有批准仍记为待决定。

复验在可比较条件下重现原动作，再检查受影响的相邻状态。例如修复提交错误后焦点丢失，应走完“失败—定位—修正—重试—成功”，而不只检查错误文案是否出现。纯合成示例没有真实失败或修复证据，不能填写产品通过结论。

## 自动检查之后仍需人工判断

记录工具版本、规则集、运行环境、页面状态、原始结果及检查范围。axe-core 的 README 明确存在需要人工判断的 `incomplete` 结果；这里仅采用其自动检查边界，不要求安装工具，也不将其能力扩展到原生客户端。[S21](../references/sources.md#s21)

保留工具原始 `incomplete`，关联的人工检查在未执行时记 `NOT_RUN`；因缺少目标环境等前提无法继续时记 `BLOCKED` 并说明原因。实际复核后再给该检查结论。怀疑误报时记录复现条件和判定依据，不通过删除告警取得通过。自动检查无发现，也不证明焦点恢复、业务结果和整个流程已经验证。

[完整表单示例](../examples/form-submit-recovery.md)把正常、字段拒绝、明确失败、结果未知、重复操作与辅助输入列为待执行项。采用时以项目实际风险选择范围，并填入真实产物、动作和证据；本仓库没有运行该表单。

## 结果与停止

每项写 `PASS`、`FAIL`、`BLOCKED`、`NOT_RUN` 或 `NOT_APPLICABLE`，附范围与证据；不适用需理由，没做不能算通过。验证失败时提出新的可检验假设，重试与操作上限服从当前任务规则，不在本设计指南中增加统一“三次”条款。

先自检，再由独立审阅者查看关键原始证据、改动区域及受影响相邻状态。作者自审不能代替独立性。剩余缺口明确交接，最终签收归项目指定负责人；本仓库不会自动放行任何产品。
